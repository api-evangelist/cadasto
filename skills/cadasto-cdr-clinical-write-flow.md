# Cadasto CDR clinical write flow

Every operationId below exists in a Cadasto-published OpenAPI document. Do not invent others.

## 0. Get a token

`POST https://{mycompany}.auth.prod.cadasto.io/oauth/token` with HTTP Basic
(`client_id`:`client_secret`), `grant_type=client_credentials`,
`audience=https://{mycompany}.api.prod.cadasto.io/openehr/v1`, and `scope=api.read api.write`.

The response has no `refresh_token`. Read `expires_in` (typically 3600) and re-request before it
lapses. Send `Authorization: Bearer <access_token>` on every call below.

Errors here are RFC 6749 §5.2 shaped: `invalid_client`, `invalid_grant`, `invalid_request`,
`invalid_scope`.

## 1. Find or create the EHR

- Look up by subject first: `ehr_get_by_subject` (`GET /ehr?subject_id=...&subject_namespace=...`).
- Only create if nothing came back: `ehr_create` (`POST /ehr`), optionally with an `EHR_STATUS`
  body and `Prefer: return=representation` to get the object back.
- By id: `ehr_get_by_id` (`GET /ehr/{ehr_id}`).

If the subject already has an EHR, `ehr_create` returns **409 Conflict**. Treat 409 as "already
exists, go read it", not as a failure.

To link the new EHR to an existing Cadasto PERSON, send the `cadasto-person-uid` header on the
create. **This link is append-only** — an EHR that already carries a link cannot be re-linked, and
there is no unlink operation. Get it right the first time.

## 2. Make sure the template is there

- List: `definition_template_adl1.4_list` (`GET /definition/template/adl1.4`).
- Upload if missing: `definition_template_adl1.4_upload` (`POST /definition/template/adl1.4`,
  `Content-Type: application/xml`, an ADL 1.4 Operational Template).

Uploading a template whose `template_id` already exists does **not** overwrite it. Both versions
survive, addressed as `{template_id}::{uid}`, and existing compositions stay valid against the
version they were committed with.

## 3. Shape the payload from a real example

`definition_template_adl1.4_example_get`
(`GET /definition/template/adl1.4/{template_id}/example`) returns a fully populated example
COMPOSITION for that template. Use it as the skeleton. This is the only rehearsal facility Cadasto
publishes — there is no validate-only mode and no `?dry_run`.

Cadasto does **not** support the openEHR FLAT / Simplified Data Template format. Send canonical
JSON (or XML), or use the Cadasto-specific Datamap endpoints under `/extra/v1/datamap/*`.

## 4. Commit the composition

`composition_create` (`POST /ehr/{ehr_id}/composition`, `Prefer: return=representation`).
Returns **201** with a `Location` header pointing at the versioned URI.

**There is no `Idempotency-Key` on this operation.** If the call times out and you retry, you will
create a second clinical document. Before retrying a create, read back with AQL (step 6) or
`composition_get` and confirm it did not land.

If you need several objects to land atomically, use `contribution_create`
(`POST /ehr/{ehr_id}/contribution`) instead of several separate creates. That is openEHR's
transaction primitive and it is the right tool for a multi-object write.

Expect **422 Unprocessable Entity** when the composition does not validate against its template.
Go back to step 3 and diff against the generated example.

## 5. Update or delete safely

- Update: `composition_update` (`PUT /ehr/{ehr_id}/composition/{versioned_object_uid}`) with
  `If-Match: "<latest_version_uid>"`. A **412 Precondition Failed** means someone wrote first —
  re-read the latest version and retry. Never strip `If-Match` to make a 412 go away; that is the
  lost-update you were being protected from.
- Delete: `composition_delete` (`DELETE /ehr/{ehr_id}/composition/{version_uid}`). This is a
  **logical** delete — the data stays in version history for audit — but **no restore operation is
  published**, so recovering it is a support conversation, not an API call.
- To roll back an update, read the prior version with
  `versioned_composition_version_get_by_id` and re-commit it as a new version. Version history is
  retained, so an update is always recoverable in practice.

Physical deletion lives in the Admin API (`admin_ehr_delete`, `admin_ehr_delete_all`,
`admin_ehr_merge`, `admin_ehr_delete_composition`, `admin_template_delete`). Those are
**irreversible** and reachable with the same coarse `api.write` scope as an ordinary commit. Do not
call them as part of a routine flow.

## 6. Read it back with AQL

`query_execute_adhoc_query_body` (`POST /query/aql`) with a JSON body:

```json
{
  "q": "SELECT e/ehr_id/value, c/uid/value FROM EHR e CONTAINS COMPOSITION c WHERE e/ehr_id/value = $ehr_id",
  "query_parameters": { "ehr_id": "<the ehr_id>" }
}
```

Always parameterise with `query_parameters`; do not concatenate values into the AQL string.

The Query API is the only surface in Cadasto that declares **408 Request Timeout** — on all six of
its operations. A 408 means the query was too broad: add `WHERE` constraints or page with AQL
`OFFSET` / `FETCH` and retry. Pagination exists here and nowhere else in the surface.

## Cross-cutting rules

- No rate limits, no `RateLimit-*` headers and no `429` are published anywhere. Back off on your
  own schedule; you will get no runtime signal.
- No error response in any Cadasto contract carries a body schema. Branch on status code, not on
  a parsed error object.
- `501 Not Implemented` is a permanent capability gap (8 operations, 5 of them in the Definition
  API), not a transient fault. Do not retry it.
- Full detail: `conventions/cadasto-conventions.yml`, `errors/cadasto-problem-types.yml`,
  `authentication/cadasto-authentication.yml`, `scopes/cadasto-scopes.yml`.
